# 技术可行性分析：《校园规则怪谈：自管委》

> 结论先行：**完全可行，且工作量可控**。这是一个"回合制阶段推进 + 轻量实时同步"的游戏，不是动作游戏，网络同步压力很小（每秒几次状态广播即可）。真正的复杂度在**服务端权威的状态机**与**信息隔离**（谁能看到什么）。

---

## 1. 需求拆解 → 技术要点

| 需求 | 技术要点 | 难度 |
|---|---|---|
| 开房间、邀请码、同时登录 | 房间管理 + WebSocket 长连接 | 低 |
| 显示在线人数 | 房间状态广播 | 低 |
| 昼夜阶段推进 | 服务端全局状态机 + 定时器 | 中 |
| 地图探索、AP 消耗 | 节点图数据结构，服务端结算 | 低 |
| 规则篡改 vs 规则比对 | 规则版本管理（规则板 = 服务端下发快照） | 低 |
| 检举核验 | 服务端记录违规事件，按 (玩家, 规则, 日期) 查询 | 低 |
| 信息隔离（自管委密谋、幻觉污染） | 按身份/状态过滤下发数据，**必须服务端做** | 中 |
| 匿名投票 | 服务端收集，匿名聚合后广播 | 低 |
| 防作弊 | 所有判定服务端权威，客户端只做展示 | 架构纪律 |

## 2. 网络架构选型（四选一）

### 方案 A：Node + ws（或 Colyseus）自建服务器 —— **推荐 MVP**
- 服务端 Node.js + TypeScript，`ws` 库或 Colyseus（自带房间抽象、断线重连、状态同步）。
- 部署：Render / Fly.io / Railway 免费档即可跑 6–12 人小房间；或任何一台 VPS / 你自己的电脑开服（朋友联机完全够）。
- 优点：逻辑完全自控，与玩法复杂度匹配；Colyseus 的 Room 模型和"房间制"天然对应。
- 缺点：需要自己处理部署与运维（但免费档够用）。

### 方案 B：Cloudflare Workers + Durable Objects
- 每个房间 = 一个 Durable Object 实例（有状态、单线程、全局就近接入），WebSocket 原生支持。
- 优点：免费额度慷慨、延迟低、无运维、水平扩展免费；非常适合"邀请码房间"模型。
- 缺点：DO 编程模型有学习成本；CPU 时间限制要求逻辑保持轻量（本游戏完全够）。

### 方案 C：PeerJS / WebRTC 纯前端（P2P 网状连接）
- GitHub Pages 托管前端 + 公共 PeerJS 信令服务器，零游戏服务器成本。
- 缺点：**必须选一个玩家主机 authoritative**，主机退出即全员掉线；断线重连、作弊防护都弱；手机网络下 NAT 穿透失败率高。
- 结论：只适合"快速试玩 demo"，不适合作为正式方案。

### 方案 D：Supabase Realtime / Firebase
- 用 Presence 做在线状态、Realtime Broadcast 做消息。
- 优点：开发快，免服务器。
- 缺点：房间逻辑仍需自己写"权威节点"（云端函数无状态、不适合做阶段定时器），容易写成客户端权威导致作弊。

### 选型建议
- **想最快玩上**：方案 A + Colyseus，部署到 Render 免费档。
- **想长期零成本运营**：方案 B（Cloudflare DO）。
- 两者代码结构可保持同构（都是 TS + WebSocket + 服务端权威状态机），先 A 后 B 迁移不难。

## 3. GitHub 在其中的角色（有 GitHub 账户即可开工）

GitHub 能提供：
- ✅ 代码托管、分支协作、Code Review
- ✅ **GitHub Pages**：托管游戏前端（静态页面，免费 HTTPS）
- ✅ **GitHub Actions**：CI（类型检查、单元测试、自动构建部署）

GitHub **不能**提供：
- ❌ 长连接游戏服务器（GitHub Pages 是静态托管，不支持 WebSocket 服务端；Actions 是短时任务运行器，不适合实时服务）
- → 因此服务器部分仍需 Render/Fly/Cloudflare/VPS 之一（均有免费档）。

工作流示例：push 到 `main` → Actions 跑测试 + 构建前端 → 自动部署前端到 GitHub Pages + 自动部署服务端到 Render。

## 4. 推荐技术栈

| 层 | 选型 |
|---|---|
| 语言 | TypeScript 全栈（前后端共享类型定义，协议即类型） |
| 前端 | React + Vite；地图用 Canvas 或轻量 SVG（本游戏不需要 Phaser 级别的游戏引擎，省一个学习成本） |
| 通信 | WebSocket，JSON 消息；消息协议按 `type + payload` 设计 |
| 服务端 | Node + Colyseus（或裸 `ws` 自写房间管理，代码量也不大） |
| 状态机 | `lobby → day_explore → night_vote → night_conspiracy → settle` 显式状态枚举，所有操作校验"当前阶段是否允许" |
| 存储 | MVP 不持久化（纯内存房间，散房即毁）；需要战绩/回放再接 Supabase/Postgres |
| 部署 | 前端 GitHub Pages；服务端 Render（免费档） |

## 5. 开发里程碑（单人业余节奏估算）

| 里程碑 | 内容 | 预估 |
|---|---|---|
| M1 | 房间大厅：建房/邀请码/准备/在线人数/断线重连 | 1–2 周 |
| M2 | 昼夜循环骨架：阶段计时、地图节点移动、AP、HP/SAN | 1–2 周 |
| M3 | 规则系统：规则板下发、每晚篡改、旧校规笔记、幻觉文本污染 | 1–2 周 |
| M4 | 核心对抗：违规记录、检举核验、自管委密谋频道、能力、匿名投票、结算 | 2–3 周 |
| M5 | 平衡调优 + 美术音效 + 压力测试（多开模拟 12 人） | 持续 |

总计 MVP 约 **6–10 周**（业余节奏）。美术可先极简（文字 + 色块地图），验证玩法后再补。

## 6. 风险与对策

1. **信息泄露（最大风险）**：身份、密谋、投票数据一旦经客户端过滤就会被人抓包看穿。→ 铁律：**服务端按接收者身份组装消息**，客户端永远只收到"自己配看的数据"。抓包只能看到自己频道的内容。
2. **玩家中途退出**：身份类游戏的常态。→ 90 秒重连 + 出局转观察者，房间不因此中断。
3. **平衡性崩坏**（如自管委连跳检举碾压）：检举额度、SAN 扣减、投票平票规则都要留配置项，先上线朋友局快速迭代数值。
4. **刷分/多开**：MVP 阶段不防（邀请码制即门槛），真要公开运营再加设备指纹/账号。

## 7. 建议的第一步

用 Colyseus 搭 M1：一个能建房、发码、看到"在线 3/8 人"的最小 demo，push 到 GitHub 并部署 Render 免费档——当晚就能让朋友连上。之后每个里程碑都能独立试玩验证。
